# Pixeler

Pixeler is a research application for analysing whether image-processing techniques traditionally used for image compression can be used to convert modern PBR materials into a pixel-art style.

The project is being developed as part of the thesis:

> **Analysis of Color Quantization and Dithering Algorithms in the Automatic Conversion of PBR Materials to a Pixel Art Style**

The application provides a Raylib-based 3D viewport, PBR texture handling, K-means color quantization, nearest-neighbor scaling, and a palette preview. The remaining algorithms, image-quality metrics, performance measurements, and comparative experiments are planned research components.

## Project objective

The main objective is to compare color quantization and dithering algorithms when processing PBR textures and to evaluate the trade-off between visual detail preservation and processing performance.

The intended workflow is:

1. Load a textured 3D model and its PBR textures.
2. Select a quantization and dithering algorithm.
3. Process the material textures.
4. Preview the original and processed materials in a common 3D viewport.
5. Measure processing performance and palette usage.
6. Compare the original and processed results using SSIM, LPIPS, and palette-usage analysis.
7. Analyse the relationship between visual quality and performance.

## Implementation status

The status below reflects the current state of the repository.

| K-means quantization | **Implemented** | K-means color quantization with a configurable number of requested colors and a 20-iteration limit. |

## Implemented features

- Load Wavefront OBJ, GLB, and GLTF models.
- Select diffuse and normal textures.
- Select metallic, roughness, and ambient-occlusion textures independently.
- Combine metallic, roughness, and AO grayscale textures into an MRA texture:
  - Red channel: metallic
  - Green channel: roughness
  - Blue channel: ambient occlusion
- Reduce the number of colors using K-means quantization.
- Downscale and upscale textures with nearest-neighbor sampling.
- Preview the source, quantized, downscaled, and upscaled images.
- Display the palette generated by the quantizer.
- Preview the processed textures on a lit 3D model.

## Planned research features

The following features are required to complete the planned research scope:

- Uniform and Median-Cut color quantization.

- A consistent algorithm-selection interface in the application.
- A controlled set of high-poly models with PBR textures at 1024x1024, 2048x2048, and 4096x4096 resolutions.
- SSIM and LPIPS evaluation between original and processed results.
- Palette-usage statistics, including color frequency and coverage.
- Processing-time and resource-usage measurements.
- Exportable experiment results for later statistical analysis.

- Comparative analysis linking visual-quality metrics with performance metrics.

## Requirements

- Go `1.25.6` or a compatible Go version.
- CGO enabled (`CGO_ENABLED=1`).
- A C compiler and native build toolchain supported by `raylib-go` (for example, MinGW-w64 on Windows or GCC/Clang on Linux).
- A desktop environment supported by Raylib.
- Native graphics/windowing libraries required by `raylib-go`.

The module dependencies are declared in [go.mod](./go.mod).

## Running locally

From the project root:

```bash
go env -w CGO_ENABLED=1
go mod download
go run .
```

Alternatively, build an executable:

```bash
go env -w CGO_ENABLED=1
go build -o pixeler
```

On Windows, make sure a C compiler such as MinGW-w64 is installed and available on `PATH`. When no output name is supplied, the build produces `magisterka.exe`:

```powershell
$env:CGO_ENABLED = "1"
go build
.\magisterka.exe
```

The application expects to be started from the project root because it loads models, shaders, and placeholder textures using relative paths.

## Docker

The repository includes a [Dockerfile](./Dockerfile) that installs Linux graphics dependencies and builds the Go application:

```bash
docker build -t pixeler .
```

The application opens a graphical window, so running it in Docker also requires access to a display server. A normal desktop build is usually simpler for interactive use.

## Usage

1. Start the application.
2. Use **Load Model** to select an OBJ, GLB, or GLTF model.
3. Use the texture selectors to load the model's textures:
   - `diffuse`
   - `normal`
   - `metallic`
   - `roughness`
   - `ao`
4. Adjust the quantization value. This controls the requested number of K-means color clusters.
5. Adjust the downscaling value. A value of `1` keeps the original dimensions; larger values reduce the texture before nearest-neighbor upscaling.
6. Click **Process textures**.
7. Use **Show textures** to inspect the source and generated images.
8. Drag in the model viewport to rotate the camera. Holding **Left Ctrl** also enables camera movement.

The palette is shown along the bottom-right edge of the window after a diffuse texture has been processed.

## Processing pipeline

The currently implemented pipeline for each loaded texture is:

1. The Raylib texture is converted to a Go `image.Image`.
2. K-means clustering groups pixels into the requested number of color clusters.
3. Each pixel is replaced by the color of its assigned cluster centroid.
4. The quantized image is downscaled using nearest-neighbor sampling.
5. The downscaled image is upscaled using nearest-neighbor sampling.
6. The resulting image is loaded back into Raylib and applied to the model.

At present, this pipeline uses K-means quantization only. Dithering is not yet applied.

The K-means implementation is in [quantization/kmeans/kmeans.go](./quantization/kmeans/kmeans.go). Image conversion, scaling, and MRA construction are implemented in [utils/image/image.go](./utils/image/image.go).

## Generated files

Processing writes image files to the project directory, including:

- `output.png`
- `downscaled.png`
- `upscaled.png`
- `MRA.png`

Per-texture processed files are also written under `models/textures/processed/`, for example:

- `output_diffuse.png`
- `downscaled_diffuse.png`
- `upscaled_diffuse.png`

These generated files may be overwritten during subsequent runs.

## Current limitations

- The application currently assumes a single material at several points in the rendering setup.
- Texture processing is performed asynchronously, but the palette state is shared between the worker goroutine and the rendering loop. Additional synchronization may be needed when running with the race detector.
- K-means uses randomly selected initial centroids, so results can vary between runs.
- The quantizer requests `k` palette entries, but some clusters may remain unused for a particular image.
- Input texture dimensions must match when combining metallic, roughness, and AO textures.
- Relative asset paths mean the application should be run from the repository root.
- Only K-means quantization is currently available; the other quantization and dithering algorithms described in the thesis scope are not implemented yet.
- No objective image-quality, palette-usage, or performance results are generated automatically.
